# Stage 01 - A Reliable First-Week Learning Alpha

**Current build stage. First active task: A411-001.**

## Outcome

The founder can open a stable phone-friendly experience, learn through an authored apartment story, save and continue, and give feedback that produces a verified improvement. Build a complete Day 1 first, then the seven-episode path. A usable small game is the deliverable, not a chatbot conversation, presentation or set of screenshots.

## Scope

| Include now | Defer |
|---|---|
| One apartment; Camille, Noé and Croissant; small additional scene panels as later episodes need them. | A navigable city, autonomous NPC society, multiplayer and complex economics. |
| Clickable objects, short pixel-styled scenes and meaningful choices. | Full walking/collision systems before they are needed, large animation libraries and generated video. |
| Real French audio, replay, subtitles and optional Chinese help. | Unlimited free-form AI conversation and automatic pronunciation certification. |
| Authored learning content, simple adaptive support and evidence logs. | A custom learning-model infrastructure or claims of validated proficiency. |
| A plant, factual chronicle, private journal, pause/resume and export/recovery. | Plant genetics, NFT features, payment systems and app-store distribution. |
| A generated shareable feedback summary. | Unapproved collection of private journals, recordings or automatic cross-device synchronization. |

The scene interface can initially use static pixel compositions and a few actions. Readability, sound, continuity and meaningful interaction take priority over a large map. This is a temporary delivery choice, not a change to `FINAL_PROJECT.md`.

## Implementation approach

Inspect existing code and permissions first. With no suitable project, choose a small browser-based implementation with few moving parts. Use prepared content and local rules so released lessons do not require live LLM calls. The development team may use AI; game runtime and development usage are different budgets.

The CTO chooses the stack within `CEO.md`. Do not add an engine, server, database service or agent framework without an immediate requirement. Audio can use an actually verified device voice or a licensed fixed recording. If audio fails, show the failure and offer a reading fallback; do not label it listening practice.

Prefer one stable preview address on an approved destination. A local artifact is useful progress but not proof the founder can open it on a phone. First exposure/publication needs the approval described in `CEO.md`; existing project-level authorization can cover subsequent low-risk preview updates.

## Delivery sequence

### A411-001 - Move-in day

Deliver one complete roughly 10-15 minute episode, with the option to pause much sooner. Implement Day 1 from `CURRICULUM_WEEK_01.md`: introductions, plant care, the cat encounter, an actual choice, a small comprehension check and a diary entry.

On return, preserve the exact scene, decision, care state and learning attempts. Provide French playback, replay and help. Include a readable version identifier, save export/import and a shareable summary.

Finish and check this slice before building the remaining six. Do not fill an hour with repetitions or seven empty chapter buttons. Mark future episodes honestly as unavailable.

### A411-002 - A continuous first week

Extend Days 2-6 one complete episode at a time. Carry forward decisions and language evidence; introduce the later characters and locations only as the episodes require them. Add contextual recurrence and per-target support adjustment. A "day" is a learning chapter, not a compulsory real-date login.

The founder's real feedback should shape at least one improvement. Do not restart their progress to demonstrate a new version.

### A411-003 - Verify and stabilize

Add Day 7, the baseline-aware first-week check and a later retention check. Validate the end-to-end records, data recovery and the feedback path. Report observed abilities, assistance still needed and missing evidence separately.

Stage 01 is complete when the seven episodes are usable, learning evidence and persistence work, and one actual feedback-to-improvement cycle has been demonstrated. This is not a CEFR certification or proof that the curriculum works for all beginners.

## Minimum persistent information

Use the simplest storage suitable for the prototype. These are required information categories, not instructions to create separate databases.

| Category | Minimum information |
|---|---|
| World | Episode/scene/checkpoint, completed events, choices, relevant character knowledge and relationship consequences. |
| Plant | Last care, current care state, growth/mementos; one care action cannot be counted twice. |
| Learning | Target, lesson/content version, input modality, audio playback status, visible support, replays, response, result type, context and time. |
| Review | Target, modality, recent evidence, next suitable encounter or due date, support recommendation. |
| Diary | Factual event references, player original, optional suggested rewrite, explicit sharing choices. |
| Save | Schema version, application/content version and recovery information. |

Record supported understanding, language-dependent discrimination, transfer and retention distinctly. No audio evidence means listening is unverified. Generated text is not learner production.

Local-only storage is a permitted starting point, not a promise of synchronization. Tell the founder its device/browser limits. Use validated import, backup before migration and failure-safe writes. Reject malformed data without overwriting the existing save. Do not include real learner records in public assets, source control or automated test fixtures.

## Feedback route

Provide one action to generate a compact shareable summary: version, session/episode, relevant learning evidence, help used and optional problem context. The founder can paste it alongside normal feedback to the CEO. This is the initial honest bridge from a phone-local save to the development team.

Private journal text and recordings are excluded by default. Do not claim automatic ingestion until a real, authorized receiving path exists. No manual data-cleaning or technical bug form should be necessary.

## Acceptance gates

| Gate | Required evidence |
|---|---|
| Usable entry | Actual artifact or preview, version and access conditions; clearly distinguish local-only from phone-accessible. |
| Mobile presentation | Main controls, readable accents/Chinese, dialogue and help work at a narrow viewport; identify real-phone testing separately. |
| Audio | Playback and replay succeed; unavailable voice/failed playback is visible. Target-phone compatibility remains pending until observed. |
| Complete interaction | Intended episode paths, a different choice, help and mid-scene pause all work; errors do not trap the player. |
| Persistence | Close/reopen and complete/resume tests retain the right world, plant, journal and learning state. |
| Recovery | Export/import round trip, bad import rejection and old-save migration preserve original data on failure. |
| Learning validity | No answer-revealing highlights in probes; support and modality recorded; assisted success not relabeled independent. |
| Privacy | Share summary excludes unapproved private content; published artifacts contain no secrets or personal saves. |
| Improvement | A real founder observation leads to a specific change, checked without losing existing progress. |

Attach actual results and environment, not blanket "all passed." Screenshots show presentation, not persistence or learning correctness. Have the team test everything it can before the founder's ordinary phone play provides the remaining device evidence.

Keep the last stable release when a core gate fails. Do not replace the active experience during a session. Clearly mark partial delivery and the smallest unresolved blocker.

Establish a recurring cycle only under the conditions in `CEO.md`.
